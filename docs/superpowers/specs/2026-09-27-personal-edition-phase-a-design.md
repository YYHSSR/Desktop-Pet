## 可选路径与选择

1. **先备份并实测宿主，再接入产品（采用）**：能把可用信号、失败边界和恢复依据固定下来，成本是先完成一次人工 Chat/Work 场景记录。
2. 直接用窗口标题、按钮文字或定时器实现联动：开发较快，但无法可靠区分完成、取消、等待和断连，不满足本次目标。
3. 先退役旧功能，最后才验证 ChatGPT：菜单工作可先完成，但旧监控与新适配的拆分边界会缺少实测依据。

## ChatGPT 状态探针

目标进程必须与实际安装包及窗口归属对应，当前仅确认本机运行的 `OpenAI.Codex_26.917.6896.0` 包含 `ChatGPT.exe`，尚未确认任何状态接口。探针先记录包版本、进程和窗口关系，再检查可公开观察的事件或 Windows UI Automation 属性。官方事件源若能实际附着当前 Chat/Work 会话，优先使用；否则只观察选定窗口的最小状态控件，不读取正文、登录数据、内部数据库或未经验证的日志格式。

在 `E:\CODX\desktop-pet\experiments\chatgpt-windows-state-probe` 保存一次性探针、运行说明和去敏结果。记录时间、模式、会话代号、状态转移、可访问性控件标识、检测延迟及失败原因；不记录提示词、回复、网址参数或凭据。观察器必须可停止，关闭后不残留轮询线程或子进程。若仅能查询控件，先实测查询开销再设活动/空闲间隔。

Chat 与 Work 分别人工触发至少 10 次正常开始及结束，并覆盖取消、错误、等待输入或审批、切换会话和模式、最小化、恢复、关闭及断连。能力矩阵按模式分别标出 `started`、`completed`、`failed`、`cancelled`、`disconnected` 是否可可靠区分，以及后台会话能否观察。无法区分的终态记为“停止/未知”；不能由超时、窗口存在或 CPU 活动推断成功。未执行的场景标记未验证。
