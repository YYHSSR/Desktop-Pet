# desktop-pet 第二轮深度审查与提速方案

日期：2026-09-28  
对象：`E:/CODE/desktop-pet`  
前提：延续“只审查，不修改项目”。本轮仅在项目外保存探针、隔离测试数据及本文。

## 1. 这轮最重要的结论

**下一轮提速应优先处理媒体准备和主线程等待，而不是继续扩大碰撞算法的 C++ 化。**

上一轮已确认：C++ 的碰撞加速不会直接改变 Python/PySide6 启动链，且稀疏碰撞不一定比 Python 快。本轮进一步找到了三个更贴近用户体感的方向：

1. **把启动海报、精确帧数和菜单缩略图在构建时生成**。当前“元数据探测”并非只读文件头，而是调用 FFmpeg 扫描整个视频。
2. **按“尽快可见”调度首帧**。当前高优预热先等全部元数据完成，再开始任何首帧工作，一个慢素材会拖延其他已经就绪的素材。
3. **让 GUI 线程真正不等待后台任务**。续圈握手仍同步等待 150 ms 预算；菜单延迟删除最终仍可能在 QThreadPool 析构时等待运行中的任务。

同时确认了新的正确性问题：共享 LRU 缓存并发读写可能抛异常、元数据重复探测、元数据进程没有进入现有捕获路径、估算元数据阻止精确元数据补齐、合法 JSON 中的无效缓存字段导致异常外溢。

这些问题有的是性能缺陷，有的是特定时序/异常数据下的可靠性缺陷。本文分别标注，不把每一种可能性都说成日常必然发生。

## 2. 新增实测与验证结果

### 2.1 媒体成本对照

使用本机 Python 3.13.15、项目当前依赖及内置 shenshen 素材。每段视频执行 3 次全片计数、3 次首帧读取；从取得的首帧在项目外生成 PNG，再读取 20 次。表中均为中位数。

| 素材 | 帧数 / 时长 | 全片帧数统计 | 启动解码器、取得首帧并关闭 | 读取预生成 PNG |
|---|---|---:|---:|---:|
| 待机呼吸休闲 | 241 / 10.04 s | 61.73 ms | 34.08 ms | 1.77 ms |
| 东张西望 | 241 / 10.04 s | 63.61 ms | 45.07 ms | 1.82 ms |
| 三球抛接 | 241 / 10.04 s | 69.77 ms | 34.34 ms | 1.96 ms |

边界说明：

- 这是文件缓存可能已热的局部实验，不是重启电脑后的冷启动。
- FFmpeg 可执行文件查找在计时前预热，避免把首次 exe 查找混进每个样本。
- “首帧”一列包含 generator 关闭/子进程收尾，**不能当成纯粹的首帧到达时间，更不能直接宣称显示延迟缩短了相同倍数**。
- 没有启动正式桌宠，没有测量双击到首帧、GPU 呈现、首次点击时间。
- PNG 实验只说明预生成资源可大幅降低这一局部路径的工作量。最终收益要接入启动时间轴后再验证。

## 3. 新问题一：共享元数据 LRU 并非线程安全

**级别：P2；确定性交错复现。若线上异常经 GUI 路径频繁触发，应提高优先级。**

位置：`pet/frame_cache.py` 的 `ByteBudgetLru.get()/put()`；`pet/webm_clip.py:104`、`:1317`、`:1331`、`:1355`。

`get()` 大致执行：

```python
entry = self._data.get(key)
if entry is None:
    return None
self._data.move_to_end(key)
return entry[0]
```

如果另一个线程在 get 与 move_to_end 之间插入数据、按预算逐出当前 key，最后一步会 `KeyError`。GIL 不把这几条 Python 操作整体变成一个事务。

`ByteBudgetLru` 文档本来就要求跨线程调用者按需加锁，但 `_META_CACHE` 同时由预热线程、按需元数据线程及 GUI 路径使用，相关读写没有统一锁。已有 `_META_CACHE_LOCK` 主要保护磁盘缓存写入，不能自动保护这些发生在锁外的访问。

**影响**：元数据读取偶发失败；异常可能进入动画启动/预热链。不要把它无条件描述为整个进程必然崩溃，实际影响取决于上层异常处理。

**改法**：

- 对该缓存的 get/put/pop/clear 统一使用短锁，或把线程安全封装进缓存类。
- 锁只覆盖内存查找与记账，不能持锁执行 FFmpeg 或磁盘写入。
- 针对 get 与逐出、两个 put、clear 与 get 补受控交错测试，并检查字节记账一致性。

**性能取舍**：很短的字典锁比重复探测和失败恢复便宜，但仍应测量争用；不要为了避锁改成每线程重复缓存而无意放大工作量。

## 4. 新问题二：元数据子进程绕过了既有捕获与取消链

**级别：P1 风险；捕获缺口已用真实 FFmpeg 验证，永久卡死/退出残留未实际制造。**

位置：`pet/webm_clip.py:1308–1356`、`_PopenCapture`；本机安装的 `imageio_ffmpeg/_io.py:134`。

当前 `_ensure_meta()` 调用：

```python
imageio_ffmpeg.count_frames_and_secs(path)
```

本机依赖实现用 `subprocess.check_output()` 执行类似：

```text
ffmpeg -i <video> -map 0:v:0 -vf null -f null -
```

这会扫描/处理整段视频，不是仅查询头部。该调用没有设置 timeout，也没有把进程句柄交给 clip 的首帧/reader 取消路径。

更细的缺口是：`_PopenCapture` 替换的是 imageio 模块中代理对象的 `Popen` 属性；代理中的 `check_output` 仍是标准库原函数，它调用的 `run`/`Popen` 解析在标准库自己的全局命名空间里，不会因为代理多了一个同名属性就自动被截获。

本次即使显式进入 `_PopenCapture` 上下文，实际审计到一次 FFmpeg 创建，`capture._procs` 仍为 0。也就是说，**仅在 count 调用外面补 capture 上下文不足以修复**。

`pause_warm()` 能阻止后续 clip 开始预热，并取消登记过的首帧进程；但不能据此认为正在执行的全片计数也已经取消。

**影响**：

- 隐藏、切角色、退出时，在飞的计数可能继续占 CPU/磁盘。
- 慢磁盘、异常资源或子进程异常时，预热线程可能长时间停留。
- 不能把该路径视为已经获得与 reader 相同的进程归属、Job Object 和取消保证。

**改法**：建立应用自己的媒体进程入口，显式持有 Popen；统一登记、超时、取消、终止确认和结果代次校验。不要全局 monkeypatch `subprocess.Popen`，那会影响其他库。对第三方封装无法安全控制的路径，使用一个受控 adapter 替代该具体调用。

**验收**：用受控子进程模拟延迟退出、不产出、错误输出；切角色/取消后任务不继续提交结果，且子进程在规定预算内结束。超时后允许降级播放，不能无限重试。

## 5. 新问题三：元数据没有“同资源只执行一次”的在飞任务管理

**级别：P2；已复现。**

位置：`WebMClip._ensure_meta()`、`warm_meta()`；`MovieLibrary.schedule_high_priority_warm()`、`warm_predicted()`。

`_meta_bg_kicked` 只限制 GUI 冷路径为这个对象起后台线程的次数，不约束外部预热线程同时进入 `warm_meta()`。两个线程都可在缓存未命中时进入全片探测。本次让两个调用在探测边界同时到达，计数调用发生两次。

多个 MovieLibrary/多个 clip 指向同一个资源时，也没有按资源版本共享在飞 Future。高优预热自身没有与低优预热同等的批次 in-flight 去重。

**改法**：以规范路径 + 文件版本为 key 保存共享任务。第一个调用者负责执行，其他调用者订阅结果；GUI 订阅时立即返回，不等任务。任务状态至少区分 queued/running/succeeded/failed/cancelled。

不要只给 `warm_meta()` 加一把包住整个 FFmpeg 调用的锁：那虽然减少重复，但可能把等待直接转移到调用线程，也无法在不同 clip 之间合并。

**验收**：GUI 按需、主动预热和多实例同时请求同一资源，实际只启动一次探测；失败/取消能按策略重试；一个实例离开不取消其他仍需要的共享任务。

## 6. 新问题四：估算元数据会阻止后续精确帧数补齐

**级别：P2；状态接缝已复现，真实竞态发生频率未测。**

位置：`pet/webm_clip.py:1308`，以及 reader 填充元数据和 `:2131` 的循环播放条件。

`_ensure_meta()` 入口只要 `_duration > 0` 就直接返回。reader 从流头获得时长后，可能设置 `_duration` 并估算 `_frame_count`，但 `_frame_count_exact` 仍是 False。

如果 reader 先填入这些字段、精确预热后到，后续 `warm_meta()` 就被短路。当前循环 reader 又明确要求 `_frame_count_exact=True` 才使用已知帧数循环路径。

本次模拟 reader 已得到非精确元数据的状态：duration=10.04、frame_count=241、exact=False；调用真实 `warm_meta()` 后，探测次数为 0，exact 仍为 False。

**影响**：该 clip 可能长期保留估算状态，不能启用预期的 reader 循环复用，重复播放时更容易产生进程重建。不是每次冷启动都如此，但当前状态机没有表达“能播放”和“帧数已精确”两种不同成熟度。

**改法**：分开 `basic_meta_ready` 与 `exact_frame_count_ready`。普通播放允许基础信息就绪就开始；精确计数后台独立补齐，在安全圈边界启用复用。不能在正在读取的有限/循环流中途直接切换计数语义。

**验收**：reader 先完成、计数先完成、计数失败后恢复三种顺序，均可进入正确状态；循环边界不多发/漏发 finished，不跳帧或重复显示首帧。

## 7. 新问题五：缓存 JSON 可解析不等于缓存值可用

**级别：P2；已复现。**

位置：`pet/webm_clip.py:770`、`:1324–1332`。

磁盘缓存加载仅确认顶层是 dict；读条目时对 frames/duration 做 truthy 判断后直接 int/float 转换。这一段位于后面的探测 try/except 之外。

例如缓存条目：

```json
{"frames": "not-an-int", "duration": 1}
```

本次注入后，真实 `_ensure_meta()` 抛出 `ValueError`。数值为 NaN/Infinity、不合理负值或极端数量也应纳入验证，而不只检查能否转型。

**影响**：缓存损坏、旧格式或其他写入方生成异常值时，原本可重新计算的加速数据反而影响正常播放路径。

**改法**：条目级 schema/version 校验；验证 frames 为正整数、duration 为有限正数并设置合理界限；无效条目只按 miss 处理并剔除/限频记录，不中断启动。缓存应该可丢弃、可重建。

**验收**：错误类型、空值、非有限数、极端值、部分坏条目和截断 JSON 都不能阻止有效素材播放；不得为同一坏条目每帧打印大量日志。

## 8. 新问题六：菜单强制延迟删除仍可能等待解码任务

**级别：P1 风险；Qt 底层阻塞行为已实测，正式菜单超过 3 秒的完整场景未复现。**

位置：`pet/window.py:3738` 起的菜单回收；`pet/context_menus/shared.py:227`；`pet/animation_thumbnail.py:163–193`。

当前 QThreadPool 是 submenu 的子对象。关闭菜单时：

1. 对 pool 调用 `clear()`。
2. 每 50 ms 检查 `waitForDone(0)`。
3. 60 次后，无论任务是否结束都 `menu.deleteLater()`。

但 `clear()` 不停止已运行任务；`deleteLater()` 只是把删除放进事件循环，不保证子线程池析构不等待。

本次用真实 Qt 对象验证：运行中的任务未结束，clear 后 pool 仍活跃；处理父对象 DeferredDelete 时等待约 353 ms，直到测试任务被放行。故当前“最多等 3 秒然后强制释放”的注释，不能当作 GUI 总等待上限。

缩略图侧又有 `event.wait()` 无 timeout，以及解码信号/任务取消不足；病态任务可能把删除卡住。源码里完成回调仍会 pump 待处理图标，关闭阶段也应阻止继续追加工作。

**改法**：

- 将线程池所有权移到独立的进程级媒体任务服务，菜单销毁不析构整个线程池。
- 菜单只持订阅/取消 token。关闭时取消未开始的需求，运行中任务完成后若 token 过期则不更新 QAction。
- 为子进程和同资源等待建立 deadline，删除 GUI 对象不能承担阻塞收尾职责。
- 保留 Qt 对象有效性与 queued signal 检查；不要通过直接删除运行中的 QRunnable/线程来“强行取消”。

**验收**：延迟、失败、永不返回的受控解码场景下，菜单关闭后 GUI heartbeat 持续，退出命令及时执行，后台任务按预算收口。

## 9. 三个额外的速度问题

### 9.1 首帧排在全批元数据之后，存在队头等待

位置：`MovieLibrary._warm_objects()`，约 `pet/library.py:382–464`。

现有顺序：

```text
所有 clip 的 warm_meta 完成
    ↓ join 全部 worker
所有 clip 的 warm_first_frame 开始
```

本次用一个快素材和一个被事件阻塞的慢素材验证：即使快素材元数据已经完成，其首帧仍不能开始。

**建议**：

- 首帧本身不必等待精确全片帧数；优先为当前待机/正在请求的动作生成可显示图像。
- 根据任务依赖做调度，而不是“两阶段全局 join”。
- 当前素材首帧 > 当前交互必要资源 > 下一个预测动作 > 精确计数 > 长尾图标，优先级可按使用情境调整。
- 设置进程级并发总预算。每库高优 3 worker、低优 1 worker、按需线程和缩略图额度会叠加，随机 sleep 不能替代总量控制。

这会降低“已经可完成的工作被另一段慢素材拖住”的延迟，不能保证减少总 CPU 工作量；后者还需要预生成与去重。

### 9.2 续圈握手会在 GUI 线程等待

位置：`pet/webm_clip.py:1678–1726`；预算 `_LOOP_REARM_ACK_TIMEOUT=0.15`。

真实方法在设置 gate 后执行 Event.wait。受控无 ACK 实验耗时 155–160 ms。150 ms 是配置的等待预算，不是严格墙钟上限，操作系统调度可能使实际等待略长。

**建议**：将 rearm 改为 pending 状态，reader 用信号确认；GUI 定时检查超时后异步回退 fresh start。迟到 ACK 必须带 generation，防止已回退的旧 reader 再次生效。

不能简单删除 wait、立即返回成功，否则会重现“reader 实际已退出但上层认为在播放”的问题。需要修改状态契约，明确 started/pending/failed。

**验收**：正常、迟到 ACK、reader 退出、取消后 ACK、快速连续切换；GUI 槽只做有界的短操作，不把等后台确认算作交互主线程工作。

### 9.3 帧签名快路径之前仍有逐次文件 stat

位置：`pet/window.py:1959–2039`。

签名函数每次调用 `os.stat()`，之后才命中两秒间隔的内容指纹缓存。因此“内容指纹的稳态零文件 I/O”不等于“整个帧签名零文件系统调用”。本次 100 次完全相同的签名调用产生 100 次 stat。

**建议**：把素材版本标记维护在资源管理器中；通过文件 watcher 或低频后台校验刷新版本号，渲染线程只读取版本。强制刷新可放在切角色、重新加载资源、显式换包时。

**收益边界**：本地缓存热时 stat 可能很便宜，本轮未证明它是最大热点；但它是非必要的每帧操作，对同步盘、网络路径或繁忙磁盘更不利。优先级应低于音效启动、元数据探测和 GUI 等待。

## 10. 推荐采用的具体提速设计

### 方案 A：发布时生成素材索引、海报和缩略图

**优先级：高；直接削减运行时工作。**

每个角色构建产物建议包含：

```text
media-index.json
  schema_version
  resource_version / 构建摘要
  每段动画：相对路径、宽高、fps、精确帧数、时长
  首帧海报路径、菜单代表图路径

posters/<animation>.png
thumbnails/<animation>.png
```

内置素材的摘要在构建阶段计算，运行时利用可信版本标识；不要为了验证海报又在启动时读取所有视频算完整 hash。外部角色包有明确的异步校验与回退策略。

**预期路径变化**：

| 操作 | 当前冷路径工作 | 建议路径 |
|---|---|---|
| 启动显示宠物 | 等媒体数据到达 | 读取待机海报，后续无缝接动画 |
| 首次点击动作 | 缓存未热则等 reader 第一帧 | 立即显示对应首帧，后台 reader 接续 |
| 精确帧数 | 运行时 FFmpeg 全片计数 | 读取索引，资源变化才重算 |
| 首次展开动画菜单 | 解码到视频约 62% 处取代表图 | 读取预生成缩略图 |

代表缩略图当前不是“只解一帧”，`animation_thumbnail._decode_webm()` 会顺序读到选定帧，所以离线化不仅省进程启动，还省中间帧处理。

**验收**：缺索引、损坏 PNG、素材替换、画布/DPR/透明边缘、无缓存首次运行都能正确降级；海报不闪旧角色、不改变点击穿透范围，动画接续不重复/跳过明显动作。

### 方案 B：一个媒体任务调度器，统一预算、去重和取消

**优先级：高；同时改善速度与可靠性。**

```text
PetWindow / MovieLibrary / 菜单
       ↓ 请求 + priority + resource_version + generation
MediaTaskService
  ├─ 同 key 在飞任务合并
  ├─ 队列与并发总预算
  ├─ deadline / 取消 / 重试策略
  ├─ 原生子进程登记与清理
  └─ 完成后 queued signal 投递结果
```

可先以“前台必要解码优先，后台重任务最多 1–2 个”作为待测起点，不能把这个数当作所有机器的最佳值。播放 reader 不应与长尾缩略图争用唯一任务槽；必要时分池但设总预算。

调用方离开时取消其订阅；只有没有消费者且允许取消的任务才终止。避免一只宠物隐藏导致另一只正在用的共享解码被杀。

建议统计 queued、inflight、deduplicated、cancelled、timed_out、spawned，按任务类型区分。这样能验证优化是否真的减少了进程数和无效工作。

### 方案 C：启动最小化与分阶段音效初始化

**优先级：高；承接第一轮结论。**

窗口显示前仅保留：必要配置、实例锁、窗口/托盘最小可用状态、首张可绘制图像。历史目录清理、完整音频池、非启用服务、长尾素材准备后移。

音效不能只把所有成本推到第一次点击。建议先准备一种必要格式的一路通道，其余空闲逐步补齐，并测首帧与首次连续点击两个指标。音频设备操作的线程归属按现有 API 约束设计，不能直接把 Qt 音频对象移到任意 Python 线程。

服务按真实能力与需求启动；上一轮的 DSH 无条件轮询等门控问题仍有效，但本轮没有重复测量其节省幅度。

### 方案 D：渲染链优化要先守住像素所有权

**优先级：中，需先测热点。**

当前帧链包括 bytes → QImage.copy → QPixmap → toImage → 镜像 → 预乘格式 → Smooth 缩放 → QPixmap。部分操作可能是浅共享，不能把所有调用都当成一次完整像素复制来累加带宽。

项目已记录过共享像素/Qt 生命周期相关崩溃，**不建议为了“零拷贝”立即删掉 copy**。先明确 reader bytes、显示图像、缓存、缩放结果的所有权和跨线程边界，再做局部方案对照。

建议先尝试更低风险的方向：素材版本标记移出帧热路径；只在必要时更新 mask；检查相同 DPR/缩放的工作是否重复。之后再研究解码端缩放、ROI 或更直接的图像提交路径，每一步都验证透明边缘、命中测试和不同 DPI。

### 方案 E：C++ 继续做局部、可证明有效的工作

**优先级：中后。**

上一轮已测 native 在稀疏场景更慢，继续优化时优先降低 Python↔C++ 边界开销：连续缓冲区复用、稳定成员映射、候选对裁剪、减少对象转换。只有真实剖析确认像素处理是大头时，再考虑新增原生图像处理模块。

FFmpeg 已经承担原生解码。把“启动一个 FFmpeg 进程”的 Python 代码改写为 C++，不会自动消除进程创建、文件读取与完整扫描成本。应先减少不必要的操作，再讨论实现语言。

## 11. 怎样验收“确实更快”

### 11.1 指标分开，避免互相掩盖

| 用户感受 | 对应指标 |
|---|---|
| 双击后多久看到角色 | 进程启动到首个有效可见帧 |
| 刚出现能不能操作 | 首次拖拽/点击反馈 p50、p95 |
| 动画切换是否停一下 | 切换请求到目标首帧的延迟 |
| 菜单关闭后是否卡 | 关闭菜单到 GUI heartbeat 恢复；最长事件循环间隔 |
| 多开是否拖慢 | 进程树 CPU/内存、活跃 FFmpeg 数、帧间隔分位数 |
| 后台是否省资源 | 隐藏/闲置时唤醒次数、在飞任务、后台进程数 |
| 退出是否干净 | 主窗口关闭到进程树退出的时间与残留数 |

### 11.2 建议实验顺序

1. 固定 EXE、DLL、角色、用户开关和资源缓存条件，采当前基线。
2. 只做海报/索引原型，比较首帧及 FFmpeg spawn 数，不混入其他重构。
3. 只做音效分阶段，测首次出现与连续点击，不允许把首帧收益换成更差首次点击。
4. 引入元数据去重/取消及缓存线程安全，测并发多开、隐藏、切角色。
5. 将 GUI rearm 和菜单生命周期改成异步，测负载下最长卡顿。
6. 再比较渲染优化与原生边界优化。

每个实验采用相同机器和输入，启动顺序交替，记录样本量和分位数。先做小规模试验筛选，再增大样本建立门禁。当前少量局部样本不足以给出可靠的整机 p95。

**建议门槛而非承诺**：首帧 p95 有明显下降；首次点击、取消、退出不退化；GUI 热路径没有等待后台线程的操作；同资源并发探测计数为 1；菜单销毁不承担 worker join。
